# ADR-0001: HUB75 topology for the first physical Leddy sign

Status: accepted for the first Raspberry Pi hardware iteration

Linear: DEN-2893, parent DEN-2346

## Decision

Use chained **64×32 HUB75 RGB matrix panels** for the first Raspberry Pi Leddy sign.

The reference physical canvas is **320×32** using five 64×32 panels in one horizontal chain. Leddy continues to expose and validate a logical viewport between 100–300 pixels wide and 5–20 pixels tall; the first production viewport is **300×20**, positioned within the larger physical panel canvas with all pixels outside the logical viewport forced black.

The Raspberry Pi panel driver target is the upstream `hzeller/rpi-rgb-led-matrix` family. The upstream project supports HUB75-style panels, chained panels and multiple parallel chains, and recommends an adapter board with 3.3 V → 5 V level shifting. It also documents Raspberry Pi 5 support.

Upstream driver: https://github.com/hzeller/rpi-rgb-led-matrix

## Why HUB75

HUB75 is a better first physical target than thousands of individually addressed WS2812/SK6812-class pixels for this product:

- the hardware is natively a rectangular scanned matrix, matching Leddy's row/column renderer;
- standard 64×32 panels are designed to be chained;
- the established Raspberry Pi driver already handles scan timing, panel chaining, PWM/color depth, panel-specific multiplexing and Pi timing differences;
- a 300×20 logical display fits inside five commodity 64×32 panels without requiring a custom PCB for 6,000 individually wired pixels;
- the driver boundary remains independent from the Leddy WebSocket and playback protocol.

## Electrical architecture

The panel supply is **external regulated 5 V**. The Raspberry Pi GPIO header must not source panel power.

The exact power budget must be recalculated from the datasheet for the panel model actually purchased. As a conservative procurement/design envelope, commodity 64×32 HUB75 panels are commonly specified in the low-single-digit amp range at 5 V. Design the five-panel prototype around a **20 A worst-case panel load plus engineering headroom**, then reduce the configured limit only after measuring the actual panels.

Reference guidance:

- https://learn.adafruit.com/raspberry-pi-led-matrix-display/hardware
- https://learn.adafruit.com/adafruit-rgb-matrix-bonnet-for-raspberry-pi/overview

Prototype distribution requirements:

- one regulated 5 V supply sized for the measured/published panel maximum with at least 20% headroom;
- a common signal/power reference ground between Pi adapter and panel supply;
- **separately fused panel branches** rather than routing the whole display through one small connector or PCB trace;
- branch fuse values and wire gauge chosen from the actual panel current, cable length, connector rating and installation conditions; do not hard-code a fuse value before the exact panel and harness are selected;
- power injection/distribution to every panel rather than assuming HUB75 ribbon cables carry panel power;
- short HUB75 signal ribbons and mechanically keyed connectors;
- a proper buffered/level-shifted Pi adapter board. The upstream driver recommends active level shifting; an Electrodragon three-channel adapter or electrically equivalent buffered board is an acceptable reference target.

## Pi and driver configuration

Initial reference geometry:

```text
physical panel rows:    32
physical panel columns: 64
chain length:           5
parallel chains:        1
physical canvas:        320 × 32
logical Leddy viewport: 300 × 20 maximum for first sign
```

The helper owns HUB75 physical mapping. Leddy sends **logical row-major pixels**, not `FrameBuffer::device_order()` output, because the HUB75 driver is responsible for panel scan/chaining/multiplexing details.

Expected upstream options begin with the equivalent of:

```text
--led-rows=32
--led-cols=64
--led-chain=5
--led-parallel=1
```

Panel-specific multiplexing, row-address type, RGB sequence and GPIO slowdown are installation parameters discovered against the exact purchased panel and recorded with that hardware revision.

## Runtime boundary

Keep the MIT-licensed Rust Leddy agent independent of the HUB75 implementation through a **separate helper process**.

The Rust process will:

1. retain API/WebSocket, configuration persistence, playback and telemetry ownership;
2. render canonical logical frames with `leddy-lib`;
3. crop/pad the logical frame into a 320×32 physical raster;
4. send framed raster data to a configured helper over stdin;
5. treat helper exit/write failure as a device error and reconnect/restart according to bounded policy;
6. use the existing snapshot backend in CI when no helper is configured.

The helper may be packaged from `rpi-rgb-led-matrix` or another validated HUB75 implementation without embedding its implementation into the Rust crate.

## Licensing boundary

`hzeller/rpi-rgb-led-matrix` is GPL-2.0-or-later and its upstream README explicitly calls out source-availability obligations for products using it. Keeping it as a separately packaged helper makes the software boundary explicit and prevents us from accidentally presenting the MIT Rust crate as if it directly incorporated GPL code. Distribution packaging still needs a license/compliance review before shipping a combined appliance; this ADR is an engineering boundary, not a legal opinion.

## Safety behavior

- Boot with the physical raster black before accepting a `show` command.
- `clear` writes a black physical frame immediately.
- Pixels outside the configured logical viewport are always black.
- On configuration change, blank before applying geometry changes.
- On helper failure, stop claiming successful frame presentation and emit/report the device error state.
- On process shutdown, attempt one final black frame before closing the helper.
- Matrix power is switched/removed only after the display has been blanked; GPIO must not back-power an unpowered panel.
- Keep USB/SSH recovery access to the Pi independent of the panel power distribution.

## First hardware acceptance run

The first physical run must record:

- exact Raspberry Pi model and OS/kernel;
- exact panel manufacturer/model/revision and scan/multiplexing settings;
- adapter/level-shifter model;
- supply model, nominal voltage and current rating;
- branch fuse and wire specifications;
- idle, representative and full-brightness measured current;
- achieved refresh rate and visible artifact check;
- a 30-minute 300×20 scrolling soak with telemetry and emergency-clear evidence;
- shutdown/restart/reconnect behavior.

If the selected 64×32 panel cannot meet refresh, color order, signal-integrity or thermal expectations, change the panel-specific installation settings first. A different panel topology requires a new ADR rather than silently changing this contract.
